# VELOCITY CUP 2026 大会運営Webアプリ仕様書

## 1. 概要

本システムは、フットサル大会「VELOCITY CUP 2026」の試合スケジュール、ライブスコア、順位表、トーナメント、管理者操作をブラウザーで確認・操作するための大会運営Webアプリである。

試合データは Cloudflare の Durable Object に保存し、同じ Worker の API 経由で読み書きする。変更は WebSocket で全端末へ即時に配信する（詳細は10章）。

## 2. 技術構成

- UI: React 18
- 言語: TypeScript
- ビルドツール: Vite
- ルーティング: React Router
- 実行環境: Cloudflare Workers（静的アセット配信と `/api/*`）
- データ保存: Durable Object `TournamentRoom` の SQLite
- 配信: WebSocket（Hibernation API）
- スタイリング: CSS
- 開発サーバー: Vite Dev Server（`@cloudflare/vite-plugin` で Worker と Durable Object をローカルの workerd 上で動かす）
- テスト: vitest（Worker 側は `@cloudflare/vitest-plugin` で workerd 上で実行）

ビルドコマンド:

```bash
npm run build
```

## 4. 大会データ仕様

### 4.1 チーム

- グループ数: 8
- グループ識別子: A〜H
- 1グループのチーム数: 5
- 総チーム数: 40

### 4.2 グループステージ

- 1グループあたり10試合。
- 全8グループで80試合。
- 試合IDは `G-{Group}-{番号}` 形式。
- グループ試合はCourt 1〜3に割り当てる。ただしCourt 3は12:15から使用する。
- 開始時刻は2026-09-26 09:00（Asia/Tokyo）から15分刻みで31スロット。12:15より前のスロットは最大2試合（Court 1・2）、12:15以降は最大3試合（Court 1〜3）を割り当てる。

### 4.3 ノックアウト

- Round of 16
- Quarter-finals
- Semi-finals
- Final
- ノックアウト合計15試合。
- 3位決定戦は設けない。
- 試合時間（ハーフタイム込み）:
  - Round of 16: 18分
  - Quarter-finals（ベスト8）・Semi-finals（ベスト4）: 7分ハーフ・ハーフタイム1分の計15分
  - Final: 10分ハーフ・ハーフタイム3分の計23分
- グループステージ終了後、および各ラウンドの間に18分の休憩を空けて開始する。各ラウンドの開始時刻と試合数は4.4を参照。

### 4.4 大会スケジュール

全95試合を 09:00 から連続開催し、19:59 に終了する。09:00〜12:15はCourt 1・2の2コート、12:15以降はCourt 3を加えた3コートを使う。

| ラウンド | 時刻 | 試合数 |
|---|---|---|
| グループステージ | 09:00 〜 16:45（15分×31スロット。12:15より前の13スロットで26試合、以降の18スロットで54試合） | 80 |
| Round of 16 | 17:03 / 17:21 / 17:39（各18分） | 8 |
| Quarter-finals | 18:15 / 18:30（各15分） | 4 |
| Semi-finals | 19:03（15分） | 2 |
| Final | 19:36 〜 19:59（23分） | 1 |

制約は次の3つである。

- 同一コートで試合の時間帯が重ならない。
- 同一チームの試合間隔を15分以上空ける。
- Court 3には12:15より前の試合を入れない。

いずれも `src/features/tournament/schedule.test.ts` で検証している。

### 4.5 試合状態

試合状態は次の4種類。

- `SCHEDULED`: 予定
- `LIVE`: 試合中
- `PAUSED`: 一時停止
- `FINISHED`: 試合終了

### 4.6 試合項目

- 試合ID
- Round
- Group
- Court
- 開始予定時刻
- 試合時間（`durationMinutes`、分単位。グループ戦15分、ノックアウト18分）
- 状態
- ホームチーム
- アウェイチーム
- ホームスコア
- アウェイスコア
- ライブタイマー開始時刻
- 一時停止時の経過秒数

## 9. 管理者仕様

### 9.1 アカウントとログイン

| ユーザー名 | 役割 | 担当 | パスワード |
|---|---|---|---|
| `superadmin` | Super-admin | 全コート | Secret `SUPERADMIN_PASSWORD` |
| `subadmin1`・`subadmin2` | SubAdmin | Court 1 | Secret `SUBADMIN_PASSWORD`（6人共通） |
| `subadmin3`・`subadmin4` | SubAdmin | Court 2 | 同上 |
| `subadmin5`・`subadmin6` | SubAdmin | Court 3 | 同上 |

- `/superadmin` はパスワードだけ、`/subadmin` はユーザー名とパスワードを入力する。ユーザー名の大文字小文字と前後の空白は区別しない。
- ログインに成功すると、サーバーが署名した `session` Cookie（HttpOnly・Secure・SameSite=Strict、12時間）を発行する。ログイン状態はブラウザーに保存しない。
- 同じユーザー名で5回続けて失敗すると、60秒間ログインできない。
- 「Sign out」でログアウトする。
- ヘッダーの管理リンクは開発環境でのみ表示する。本番では `/superadmin`・`/subadmin` を直接開く。
- 開発環境のパスワードは `.dev.vars`（見本は `.dev.vars.example`）。本番は `wrangler secret put` で設定する。
- セッションは12時間で切れるため、大会当日の朝にログインすること（前夜のログインは大会中に失効する）。
- Cookie は `Secure` 属性付きのため、`http://<LAN IP>` で開発サーバーにスマートフォンからアクセスしてもログイン状態を維持できない。`localhost` か https トンネル経由でテストすること。

### 9.2 権限

| 操作 | 未ログイン | SubAdmin | Super-admin |
|---|---|---|---|
| 閲覧（`GET /api/state`・WebSocket） | 可 | 可 | 可 |
| 試合の得点・状態の変更 | 不可（401） | 担当コートの試合のみ（他は 403） | 全試合 |
| Seed knockout teams・Reset all matches | 不可（401） | 不可（403） | 可 |

SubAdmin の画面には担当コートの試合だけを表示し、Seed knockout teams と Reset all matches の区画は表示しない。

### 9.3 試合操作

選択した試合の状態（Not started / ● LIVE / Ⅱ PAUSED / ■ Finished）とタイマーを、試合操作の上に大きく表示する。試合選択リストにも、未開始以外の試合には状態を併記する。

Super-admin と SubAdmin は選択した試合に対して以下を実行できる。

- ホーム・アウェイスコアを1点増減。押すたびに即時保存し、全端末へ反映する。未開始の試合では操作できない。
- 操作ボタンは状態に応じて表示を切り替える。

| 現在の状態 | 表示するボタン | 動作 |
|---|---|---|
| `SCHEDULED` | ▶ Start match | `LIVE`にし、タイマーを0から開始する |
| `LIVE` | Ⅱ Pause | `PAUSED`にし、経過時間を保存してタイマーを止める |
| `LIVE` / `PAUSED` | ■ Finish match | `FINISHED`にし、最終の経過時間を保存する |
| `PAUSED` | ▶ Resume | `LIVE`に戻し、止めた時点の続きからタイマーを進める |
| `FINISHED` | なし | — |

### 9.4 大会運営操作

Super-admin 画面の「SUPERADMIN SETUP」には、選択中の試合とは別に大会全体に対する操作がある。

- **Seed knockout teams**: グループステージの順位からRound of 16の対戦相手のみを埋める。試合時刻・Courtは変更しない。
- **Schedule check**: 現在の全試合についてコートの二重予約の有無と最終試合の終了時刻を実際に計算して表示する（例: `ⓘ Schedule check: 95 matches, no court clashes, finishing 19:59.`）。コート重複がある場合は該当する試合IDの組を表示する。
- **↺ Reset all matches**: 全95試合をスコア・タイマー未設定の初期状態に戻す。ボタンを押すと確認メッセージが表示され、「Yes, reset」で実行、「Cancel」で取り消す。通常のリセット手段はこのボタンである（詳細は10章）。

## 10. データ同期仕様

試合データは Cloudflare の Durable Object `TournamentRoom`（名前 `main` の1インスタンス）の SQLite を唯一の正本とする。ブラウザーは Worker の `/api/*` 経由で操作し、変更の結果は WebSocket で全端末へ配信される。

### 10.1 API

| メソッド | パス | 権限 | 用途 |
|---|---|---|---|
| `POST` | `/api/login` | 誰でも | ログイン。成功すると `session` Cookie を発行 |
| `POST` | `/api/logout` | 誰でも | `session` Cookie を削除 |
| `GET` | `/api/session` | 誰でも | ログイン中の利用者（`{"session": null}` なら未ログイン） |
| `GET` | `/api/state` | 誰でも | 全試合とversionを返す |
| `GET` | `/api/ws` | 誰でも | WebSocket。接続時に全state、以後は更新のたびに配信 |
| `PATCH` | `/api/matches/:id` | Super-admin・担当コートの SubAdmin | 1試合の部分更新 |
| `PUT` | `/api/matches` | Super-admin | 全置換 |
| `POST` | `/api/reset` | Super-admin | 全試合を未開始へ戻す |

変更系（`POST`・`PUT`・`PATCH`・`DELETE`）は `content-type: application/json` が必須で、違えば `415`（`UNSUPPORTED_MEDIA_TYPE`）を返す。未ログインは `401`（`UNAUTHENTICATED`）、権限なしは `403`（`FORBIDDEN`、担当外コートは `WRONG_COURT`）。ログインの失敗は `401`（`INVALID_CREDENTIALS`）、試行制限中は `429`（`TOO_MANY_ATTEMPTS`、`Retry-After` ヘッダー付き）、Secret 未設定は `500`（`AUTH_NOT_CONFIGURED`）。

### 10.2 更新の流れ

スコアや状態の編集など、試合単位の操作は `PATCH /api/matches/:id` として送られる。Seed knockout teamsは `PUT /api/matches`、Reset all matchesは `POST /api/reset` を使う。Durable Object は該当の試合だけを書き換え、`version` を1つ増やして保存し、接続中の全 WebSocket へ `{"type":"state","state":...}` を送る。クライアントは10秒ごとに `ping` を送り、サーバーは `pong` を返す。

`PATCH` で変更できるのは `status`、`homeScore`、`awayScore`、タイマー項目、PK戦項目のみである。試合ID、Round、Court、開始予定時刻、対戦チームは変更できない。

存在しない試合IDを指定した場合は `404` で `{"error": "unknown match: ...", "code": "UNKNOWN_MATCH"}` を返す。変更できないフィールドを含めた場合は `400` で `{"error": "field is not patchable: court", "code": "FIELD_NOT_PATCHABLE"}`、値の型が不正な場合は `400` で `INVALID_FIELD_VALUE`、`PUT` で試合IDが重複している場合は `400` で `INVALID_MATCHES` を返す。リクエストボディがJSONとして解釈できない場合も `400` を返す。

### 10.3 保全

- Durable Object はリクエストを1つずつ処理するため、並行更新による取りこぼしは起きない。
- 全置換とリセットは1つのトランザクションで書き込み、途中で失敗しても半端な状態を残さない。
- 試合データはメモリに持たず、常に SQLite から読む。Durable Object が休止・退避されても内容は失われない。

### 10.4 接続断

サーバーへ接続できない場合、画面上部に切断バナーを表示し、管理操作を無効化する。最後に取得したデータは表示したままにする。クライアントは1秒から最大10秒まで間隔を延ばしながら自動で再接続し、再接続時に全stateを受け取って同期する。25秒間何も届かない接続は切れたものとみなして張り直す。

## 11. 非機能・制約

- 本番は Cloudflare Workers（無料プランを想定）で動かす。Workers と Durable Objects の無料枠は1日10万リクエストで、WebSocket の接続確立が1リクエスト、サーバーからの送信は無料。
- 複数端末・複数ユーザーでの同時編集をサポートする。同一フィールドを同時に変更した場合は後着信が優先される（明示的なロックや競合解決は段階3で入れる）。
- パスワードと署名鍵は Cloudflare の Secrets に置き、コードとビルド成果物には含めない。

## 12. 起動方法

プロジェクトルートで実行する。

```bash
npm install
cp .dev.vars.example .dev.vars
npm run dev
```

ブラウザーで起動時に表示されるURL（通常 `http://localhost:5173/`）を開く。ローカルのデータは `.wrangler/state/` に保存される。

本番へのデプロイ:

```bash
npx wrangler login                          # once per machine
npx wrangler secret put SUPERADMIN_PASSWORD # password for "superadmin"
npx wrangler secret put SUBADMIN_PASSWORD   # shared by subadmin1–subadmin6
npx wrangler secret put SESSION_SECRET      # a long random string, e.g. `openssl rand -base64 32`
npm run deploy
```

```bash
npm run lint
```
